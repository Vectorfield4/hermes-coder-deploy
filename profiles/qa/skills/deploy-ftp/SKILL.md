# Deploy FTP

## Overview
Downloads the latest release artifact (zip) from GitHub Releases and uploads it to the production server via FTP. Called by `execute-qa-task` for `type: deploy` tasks (triggered by the `/deploy-ftp` Telegram command).

## When to Use
- Manually via `/deploy-ftp` in Telegram.
- **Do not use** from the review flow — merged PRs deploy to Vercel staging instead (see `deploy-vercel`).
- Requires a GitHub Release to exist (created by `release-to-main`).

## Instructions

### 1. Input
- Receive `project` from task metadata.
- Determine the repo from project context (`memory_read(projects)` or `/workspace/<project>/.git/config`).

### 2. Find the latest release
- Use `gh release list --limit 1 --repo <repo>` to get the latest release tag.
- If no releases exist → block: "No GitHub Releases found. Run /release first to create one."
- Extract the tag name and the zip asset URL:
  ```
  gh release view <tag> --repo <repo> --json assets
  ```
- Find the `.zip` asset and get its `browser_download_url`.

### 3. Download the release zip
- Load retry protocol: `skill_view("deploy-ftp", "references/retry.md")`.
- Download the zip:
  ```
  curl -L -o /tmp/<project>-<tag>.zip "<asset_url>"
  ```
- Apply retry protocol — transient errors (timeout, network, 5xx) are retried with exponential backoff; permanent errors (auth, 404) fail immediately.
- Verify the download: `file /tmp/<project>-<tag>.zip` should report a zip archive.

### 4. Extract the zip
- Create a temp directory and extract:
  ```
  mkdir -p /tmp/<project>-deploy && cd /tmp/<project>-deploy && unzip /tmp/<project>-<tag>.zip
  ```
- If extraction fails → block with error details.

### 5. Upload to FTP
- Get FTP credentials from the environment: `FTP_HOST`, `FTP_USER`, `FTP_PASS` (injected from `secrets/ftp_host`, `secrets/ftp_user`, `secrets/ftp_pass`).
- Load retry protocol: `skill_view("deploy-ftp", "references/retry.md")`.
- Upload the extracted files to FTP:
  - Use `lftp` or `curl`.
  - Example: `lftp -u $FTP_USER,$FTP_PASS $FTP_HOST -e "mirror -R /tmp/<project>-deploy/ ./public; quit"`.
  - Apply the retry protocol — transient errors (timeout, network, 5xx) are retried with exponential backoff; permanent errors (auth, 404) fail immediately.

### 6. Cleanup
- Remove temp files: `rm -rf /tmp/<project>-<tag>.zip /tmp/<project>-deploy`.

### 7. Complete
- On success: return SUCCESS.
- On failure: return an error to `execute-qa-task` with details.

## Tools
- `gh release list`, `gh release view`
- `curl` (download)
- `unzip`
- `lftp` or `curl` (FTP upload)
- `file` (verification)

## Common Pitfalls
- **No release exists**: The deploy flow requires a GitHub Release. If none exists, the user must run `/release` first.
- **Wrong asset type**: Only download `.zip` assets. Ignore source code archives auto-generated by GitHub (`source.zip`, `source.tar.gz`).
- **FTP path wrong**: The upload path (`./public`) should match the server's document root. Adjust per project if needed.
- **Large zip files**: If the release zip is very large, the download may time out. Increase curl timeout or use `wget` with retry.

## Verification Checklist
- [ ] Latest release is found.
- [ ] Zip asset URL is extracted.
- [ ] Zip is downloaded successfully.
- [ ] Zip is extracted without errors.
- [ ] Files are uploaded to FTP.
- [ ] Temp files are cleaned up.
